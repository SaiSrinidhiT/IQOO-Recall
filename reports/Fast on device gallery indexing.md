# Decode smaller, overlap stages, defer OCR

The iQOO 15's NPU is not what limits gallery indexing. Qualcomm publishes **3.3 ms per image** for the exact SigLIP2 base-patch16-224 image encoder the app uses, as float TFLite fully on the Snapdragon 8 Elite Gen 5 NPU. That is roughly 300 images/s of model time. The current pipeline probably delivers only about **3-8 photos/s** end to end (estimate). Three things cost that time. Every photo gets a full-resolution JPEG decode, because the current `setTargetSize(…2048…)` call resolves to sample size 1. Every photo is also read whole and hashed before the gate has even rejected it. And the ~10% of documents run two ML Kit recognizers plus a Tesseract fallback that takes seconds, in the same sequential loop as the gate. Four changes should lift throughput to roughly **50-120 photos/s** (estimate), or about 10-20x. First, decode at a power-of-two sample size or through MediaStore thumbnails. Second, read and hash full bytes only for documents. Third, run three or four decoder coroutines into one dedicated NPU thread. Fourth, move OCR onto its own queue with Telugu and Devanagari work deferred to a second pass. For a 10,000-photo gallery that means about 2-3 minutes instead of 20-55. The NPU-side changes are low value at these rates: quantisation, batching, lighter gate models and performance modes each save about 1-3 ms per photo on a thread that is not the bottleneck. They matter only after decode is fixed, and some carry licence or accuracy risk. Ordering the queue Screenshots, Downloads and WhatsApp first, newest first, surfaces most documents in the first minute. At present the queue runs oldest first. For Android 16 the worker needs a `mediaProcessing` foreground service. Without it the run is capped at 10 minutes and slows sharply once the user leaves the app. Most per-stage millisecond figures on this device are unpublished, so every "after" number below is an estimate until the benchmarks at the end are run.

## Ten changes, ranked by what they buy

In this report, **(P)** marks a published measurement and **(E)** marks an estimate derived here from published ratios, source code or first principles. No source publishes Android decode, ML Kit or loadThumbnail timings on an 8 Elite-class phone, so every stage except the NPU step is (E) until measured on the device. The AI Hub numbers come from a Samsung Galaxy S26 ("8 Elite Gen 5 For Galaxy"). That is the closest published proxy for the iQOO 15's SM8850, not the same part ([HF qualcomm/SigLIP2](https://huggingface.co/qualcomm/SigLIP2)).

The baseline below is built from the code as it stands. `IndexWorker` reads each photo with `readBytes()`. `IngestPipeline` hashes it with SHA-256, decodes it with `ImageLoader.decode` (max 2048 px) and runs `SiglipVision.embed`. The worker then commits one `dao.update` and one `setProgress` per photo. Documents additionally run ML Kit Latin **and** Devanagari. Tesseract `tel+eng` follows if fewer than 40 useful characters come back.

Two of the notes gave conflicting SigLIP2 costs, and the conflict needs settling before the panel sees it. One note inferred **~10-13 ms** from AI Hub's OpenAI-CLIP ViT-B/16. That graph bundles the image and text encoders, so it overstates image-only cost ([HF OpenAI-Clip](https://huggingface.co/qualcomm/OpenAI-Clip)). The SigLIP2 perf.yaml measures the image encoder alone at **3.299 ms** on the S26 and 4.108 ms on the S25. All 551 layers run on the NPU ([perf.yaml](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/siglip2/perf.yaml)). The 3.3 ms figure is the one to use. The app's copy is the AI Hub export and already sets `HTP_PRECISION_FP16`, `HTP_PERFORMANCE_BURST` and a graph cache. It should therefore match, **provided the QNN delegate is created**. The one catastrophic risk is a silent fallback. `LiteRtModel.load` walks NPU → GPU → CPU and keeps whichever warm-up succeeds. A CPU landing turns ~3 ms into roughly 200-300 ms (E, scaled by token count from the 663 ms at 336 px). That drops the whole gallery to a few photos per second. The backend name is logged. Partial delegation is not: logcat's "Replacing N out of M node(s)" line should read 551 of 551 in one partition.

## Asking for one-eighth of the pixels removes the dominant cost

The biggest waste in the current code sits in one line of `ImageLoader.decode`. For a 4080×3072 photo, `setTargetSize(2048, 1536)` sends Skia's `computeSampleSize` to **sample size 1**, because `4080/2048` is 1 in integer division ([SkAndroidCodec](https://github.com/google/skia/blob/main/src/codec/SkAndroidCodec.cpp)). The target is not an exact sampled size, so hwui decodes into a **full-size temporary heap bitmap** and then canvas-scales it ([hwui ImageDecoder.cpp](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/libs/hwui/hwui/ImageDecoder.cpp)). That is about 50 MB of temp buffer plus a 12.6 MB output per photo (E, derived from the code path). The result is then squashed to 224×224 for a gate that rejects 90% of photos. Naively asking for 256 px does not fix it either. `setTargetSize(256, 192)` on the same file lands on sample 15. Skia gets native JPEG downscaling only for sample sizes of 2, 4, 8 or their multiples, so sample 15 **silently loses the DCT shortcut** ([SkSampledCodec](https://github.com/google/skia/blob/main/src/codec/SkSampledCodec.cpp)). The fix is `setTargetSampleSize(8)`, or `inSampleSize = 8` in BitmapFactory, which runs on the same Skia codec. This drives libjpeg-turbo's 1/8 IDCT directly and yields 510×384 with no temp buffer ([SkJpegCodec](https://github.com/google/skia/blob/main/src/codec/SkJpegCodec.cpp)). Mozilla measured IDCT-scaled decode on a desktop at **2.36x faster at 1/8, with 20x lower peak memory** ([Mozilla bug 2033250](https://bugzilla.mozilla.org/show_bug.cgi?id=2033250)). ARM phones should gain at least as much, because the full-size scale step disappears too (E). The gain is bounded because entropy decoding still touches every coefficient. The rule for the gate: read WIDTH/HEIGHT from MediaStore, choose the largest power-of-two sample that keeps the short side at 224 px or more, and scale the result once to 224.

The four acquisition routes differ mainly in where the pixels come from:

| Route | How it gets pixels | Per-image cost | Caveat |
|---|---|---|---|
| `ImageDecoder` / `BitmapFactory` at sample 8 | libjpeg 1/8 IDCT | 10-40 ms (E) | Only JPEG gets the shortcut; HEIC, PNG and WebP decode fully, then subsample |
| `ContentResolver.loadThumbnail`, cached | Opens a ~20-80 KB JPEG from `Pictures/.thumbnails` | 2-8 ms (E) | Few entries are cached on first run (unverified); rescans benefit |
| `loadThumbnail`, cache miss | MediaProvider tries HEIF thumbnail → EXIF thumbnail → full decode, then JPEG-encodes at q90 and writes | 5-15 ms with EXIF thumb; full decode + encode otherwise (E) | Runs in MediaProvider's binder threads |
| `ExifInterface` embedded thumbnail | Parses APP1 only | 2-5 ms (E) | Absent from PNG screenshots and from most WhatsApp or edited images |

`loadThumbnail` is less direct than it looks. MediaProvider **ignores the requested Size** when generating. It always builds a thumbnail at half the smallest screen edge ([MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)). On the iQOO 15's 1440-wide panel that is 720 px, or 540 px if OriginOS renders at FHD+ (unverified) ([iQOO store](https://shop.iqoo.com/in/product/2067)). The client then subsamples by an integer factor ([ContentResolver.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/core/java/android/content/ContentResolver.java)). For JPEGs, MediaProvider stores the EXIF thumbnail **with no minimum-size check** ([ThumbnailUtils.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/media/java/android/media/ThumbnailUtils.java)). The gate can therefore see a 160-512 px image. That is probably adequate for a document-or-not decision, but it is not proven. A first full pass also writes roughly 0.2-0.8 GB of thumbnails for 10,000 photos (E). The practical hybrid follows. Use sample-8 ImageDecoder for JPEGs, the common camera case, with fully predictable quality. Use `loadThumbnail` for HEIC, where the embedded HEIF thumbnail is the only shortcut, and for rescans. For PNG screenshots, accept a full decode at the lowest sample size; nothing faster exists for PNG on the first pass. Keep software bitmaps. `HARDWARE` bitmaps forbid the CPU pixel access the tensor fill needs, and `RGB_565` saves no JPEG decode time.

### Dedup should key on MediaStore, not on bytes

Hashing is cheap. Paying for it on photos the gate will reject is the waste. SHA-256 at about 2 cycles/byte ([OpenSSL](https://github.com/openssl/openssl/blob/master/crypto/sha/asm/sha512-armv8.pl)) costs a few ms per photo (E, extrapolated from older cores; no Oryon figure is published). The larger costs are the multi-MB `byte[]` allocated per photo and the fact that hashing must come before decoding. The better order is to gate first. For the ~10% of documents, then stream a SHA-256 through a reused 64-256 KB buffer, since the vault file is named by hash anyway. For cross-folder copies, compare `SIZE` first: files with a unique size cannot be byte-identical. Near-duplicates are the common case, because WhatsApp re-encodes images. The app's existing SigLIP-cosine plus OCR-Jaccard check covers them. A 64-bit dHash from the 224 px bitmap would add a microsecond-scale pre-check (E). One trap concerns location data. Without `ACCESS_MEDIA_LOCATION`, MediaProvider serves GPS-tagged photos through its **FUSE redaction path** in userspace. That path is slower than a lower-filesystem descriptor, and the bytes hashed are the *redacted* bytes ([MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java); [FUSE passthrough](https://source.android.com/docs/core/storage/fuse-passthrough)). Hashes of redacted bytes should still work for matching exact duplicates within the app (E). The per-read cost is one more reason to avoid whole-file reads on the gate path.

## A three-stage pipeline keeps the NPU fed and OCR out of the way

Once decode is cheap, the sequential loop becomes the ceiling. One decoder thread at 15-50 ms per photo (E) leaves the NPU idle more than 80% of the time. The 8 Elite Gen 5 has **2 prime cores at 4.6 GHz and 6 performance cores at 3.62 GHz, with no efficiency cluster** ([Android Authority](https://www.androidauthority.com/snapdragon-8-elite-gen-5-benchmarks-3600242/)). Three or four decoders are therefore affordable while leaving room for the UI, the NPU driver thread and OCR. The recommended pipeline has five parts:

1. **I/O producer.** A MediaStore cursor on `Dispatchers.IO` emits URIs and metadata, not bytes.
2. **Decoders.** N decoder coroutines on `Dispatchers.Default.limitedParallelism(N)` each produce a 224×224 input buffer.
3. **NPU thread.** One model owner runs on a real single-thread executor.
4. **OCR queue.** Documents go to a bounded channel with one or two OCR workers.
5. **DB writer.** One writer commits 50-200 rows per transaction.

Channels should be small and suspending. Flow's `buffer()` suspends the producer by default ([kotlinx buffer](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/buffer.html)). Avoid `flatMapMerge`: it defaults to 16 concurrent inner flows and is experimental ([flatMapMerge](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/flat-map-merge.html)). Note that `limitedParallelism(1)` "is not a mutex" and does not pin a thread ([limitedParallelism](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-coroutine-dispatcher/limited-parallelism.html)). A dedicated executor matters here. TFLite's `InterpreterApi` "instances are not thread-safe" ([InterpreterApi.java](https://raw.githubusercontent.com/tensorflow/tensorflow/master/tensorflow/lite/java/src/main/java/org/tensorflow/lite/InterpreterApi.java)), and the GPU delegate has hung when called from a thread other than its creator ([tensorflow#25657](https://github.com/tensorflow/tensorflow/issues/25657)). Today `LiteRtModel.run` is `@Synchronized` but called from whichever `Dispatchers.Default` thread is free. That is safe for correctness but leaves thread affinity to chance. Whether QNN is thread-affine is unverified. SigLIP2 and Nomic should share the one NPU thread, since a second HTP session mostly time-slices the same accelerator and doubles memory (E). Three small code-level costs also go away with this design. `SiglipVision.preprocess` allocates a `Triple` for each of 50,176 pixels. `floatInput` allocates a fresh 602 KB direct buffer per call. `run` allocates new output buffers each time. Reusing preallocated buffers saves around a millisecond and removes GC churn (E).

The OCR queue is what makes the pipeline pay off, and the arithmetic shows why. One OCR worker at 300 ms per document (E) clears about 3.3 documents/s. At 10% documents, that caps the **whole gallery at about 33 photos/s**, whatever the gate does. Two workers at 100-300 ms per document, after the OCR changes below, sustain 70-200 photos/s (E). That brings the blended rate to about **50-120 photos/s** (E), against a model-only NPU ceiling near 300/s (P). On a CPU fallback, the same topology gives no relief. Detect that case and switch strategy rather than pipelining harder.

Database writes change from per-photo to batched. Each photo currently causes two SQLite commits: `dao.update` in the app DB and `setProgress`, which WorkManager persists to its own database ([WorkManager progress](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/observe)). Android's guidance is WAL with `synchronous=NORMAL` and multi-row transactions from a single writer ([SQLite best practices](https://developer.android.com/topic/performance/sqlite-performance-best-practices)). The new flow commits one transaction per ~100 results or per 500 ms. It drives the in-app progress bar from a `StateFlow` and calls `setProgress` about once a second. The scanner's per-row `insertIfAbsent` during the first scan should also run inside a single transaction.

## Lighter gates and quantisation buy milliseconds, not multiples

At 3.3 ms per photo on a thread that is not the bottleneck, NPU tuning barely moves end-to-end throughput. It matters only once decoders push past about 200 photos/s. Every NPU option is weighed against that bar.

**Quantisation.** w8a16 cuts SigLIP2 from 3.30 ms to **2.46 ms (QNN_DLC) or 2.12 ms (ONNX)**, a 1.34-1.58x gain ([HF qualcomm/SigLIP2](https://huggingface.co/qualcomm/SigLIP2)). ViT-B/16 loses no accuracy at w8a16 (80.5% vs 80.5-80.6% float) ([vit numerics](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/vit/numerics.yaml)). CLIP ViT-B/16 COCO recall is also unchanged ([openai_clip numerics](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/openai_clip/numerics.yaml)). No SigLIP2-specific numerics are published. The catch is that AI Hub offers **no w8a16 TFLite build**, only QNN_DLC, a context binary or ONNX ([export.py](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/siglip2/export.py)). Adopting it means changing runtime. w8a8 should be avoided. On the S26, ViT-B/16 w8a8 TFLite is **slower** than float (5.21 vs 3.61 ms) and loses 2-3 points of top-1 accuracy ([vit perf.yaml](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/vit/perf.yaml)). Edge Impulse's claim that INT8 is "mandatory for HTP acceleration" is contradicted for 8 Gen 1 and later chips by AI Hub's float-on-NPU results ([Edge Impulse](https://docs.edgeimpulse.com/tutorials/topics/android/qnn-acceleration)).

**Batching.** Batch size is a static input shape fixed at export ([siglip2 model.py](https://github.com/qualcomm/ai-hub-models/blob/main/src/qai_hub_models/models/siglip2/model.py)). No source quantifies HTP batch gains for ViT, SigLIP or CLIP. Profile batch 1, 4 and 8 on AI Hub before building a micro-batcher.

**Performance modes.** AI Hub's published numbers use `kHtpBurst`, the default ([AI Hub API](https://workbench.aihub.qualcomm.com/docs/hub/api.html)). No per-mode latency or thermal data exists. `SUSTAINED_HIGH_PERFORMANCE` is the sensible choice for multi-minute runs, but its cost is unmeasured.

**Warm-up and compile caching.** Compile caching is the NPU knob with real user-visible payoff. Google measured LiteRT's cache cutting ResNet152 initialisation from **7,465 ms to 198 ms** ([LiteRT NPU](https://developers.google.com/edge/litert/next/npu)). The app already sets `setCacheDir` and `setModelToken`. The token, however, is `name-length`, which does not change if a model is replaced by one of the same byte length. Qualcomm's helper uses an MD5 of the file instead ([TFLiteHelpers.java](https://github.com/qualcomm/ai-hub-apps/blob/main/apps/_shared/android/tflite_helpers/TFLiteHelpers.java)). Nomic can load lazily, on the first document.

**Lighter gate models.** Alternatives are narrower than they look, mainly because of licences:

- **MobileCLIP / MobileCLIP2.** 3-8x faster than ViT-B/16 on iPhone. Their weights are licensed "exclusively for Research Purposes", which "does not include … use in any commercial product" ([LICENSE_MODELS](https://github.com/apple/ml-mobileclip/blob/main/LICENSE_MODELS)). Acceptable for a hackathon demo, not for a shipped app. A search snippet claimed MobileCLIP2-S2 runs in ~450 ms on a Galaxy S21, but fetching the paper did not confirm it, so treat that number as **unverified**.
- **Permissive CLIP-style options.**
  - SigLIP2 **B/32-256** (Apache-2.0): 64 tokens instead of 196, at 74.0% vs 78.2% ImageNet zero-shot ([big_vision](https://github.com/google-research/big_vision/blob/main/big_vision/configs/proj/image_text/README_siglip2.md)).
  - TinyCLIP (MIT) ([TinyCLIP](https://github.com/wkcn/TinyCLIP)).
  - OpenVision Ti/S (Apache-2.0) ([OpenVision](https://github.com/UCSC-VLAA/OpenVision)).
  - PE-Core-S16 (Apache-2.0, 72.7%, but 384 px input) ([perception_models](https://github.com/facebookresearch/perception_models/blob/main/README.md)).

  None has published Snapdragon latency.
- **Distilled classifier.** MobileNet-v3-Small runs at **0.26-0.32 ms** on 8 Elite Gen 5 (BSD-3) ([HF MobileNet-v3-Small](https://huggingface.co/qualcomm/MobileNet-v3-Small)). It could be trained on SigLIP2's own verdicts with a high-recall threshold.

Two facts make a lighter gate less attractive for this app. The current code stores no SigLIP vector for rejected photos, so a cheaper gate saves no later work. And the RVL-CDIP literature shows document-image accuracy rising with input size up to 384 px, with small text illegible at 224 px ([Tensmeyer & Martinez](https://ar5iv.labs.arxiv.org/html/1708.03273)). That is a fine-grained 16-class task, so it is only a loose warning for a binary gate. No published doc-vs-photo accuracy exists at any resolution.

**Thermals.** One 100-run study on SM8750 found NPU inference running **~10.5 °C cooler** than CPU inference, with 2.5x lower energy per request ([arXiv 2606.27906](https://arxiv.org/html/2606.27906)). A realme GT8 Pro on the same Gen 5 chip fell below 30% of peak under sustained *graphics* load ([AndroidHeadlines](https://www.androidheadlines.com/2025/11/qualcomm-snapdragon-8-elite-gen-5-thermal-throttling-heat-hot-tests.html)). That is not an NPU test. Faster-throttling claims from multicoreperformance.com have unclear sourcing and are not relied on here. The likely heat source during indexing is CPU decode, not the NPU. Scale decoders with `PowerManager.getThermalHeadroom`, polled no more than once per 10 s ([ADPF thermal](https://developer.android.com/games/optimize/adpf/thermal)).

## OCR, not the gate, sets the ceiling once decode is fixed

The current `OcrEngine.recognize` runs **both** ML Kit recognizers on every document at up to 2048 px, then Tesseract `tel+eng` whenever fewer than 40 useful characters come back. That fallback catches every sparse-text screenshot that passes the gate's leniency rule. Google publishes no ML Kit v2 latency. It does document two facts that cut the work directly. First, the Devanagari recognizer handles "Devanagari and Latin-based languages" ([ML Kit reference](https://developers.google.com/ml-kit/reference/swift/mlkittextrecognitiondevanagari/api/reference/Classes/DevanagariTextRecognizerOptions)). That comes from the iOS reference; Android behaviour is assumed to match, not verified. Second, there is "generally no accuracy benefit for characters to be larger than 24x24 pixels", and a letter-size page "might" need only 720×1280 ([ML Kit Android guide](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)). Two changes follow. Run one recognizer: Latin by default, Devanagari only when locale or a first-pass cue suggests Hindi. Decode documents with `setTargetSampleSize(2)`, which gives 2040×1536 through the native 1/2 IDCT, or smaller for screenshots whose UI text is already 30-50 px tall. Together these should roughly halve ML Kit time or better (E).

Telugu is the hard case. ML Kit supports no Telugu script ([ML Kit languages](https://developers.google.com/ml-kit/vision/text-recognition/v2/languages)). Tesseract LSTM costs **1.8-4.6 s for one Hindi page on a desktop CPU** (P) ([tessdoc](https://tesseract-ocr.github.io/tessdoc/tess4/4.0-Accuracy-and-Performance.html)), and it is effectively single-threaded on Android. The app already reuses one `TessBaseAPI`, the fix that took one Android user from minutes to under 5 s ([Tesseract4Android #20](https://github.com/adaptech-cz/Tesseract4Android/discussions/20)). Remaining Tesseract levers: use tessdata_fast, run `tel` alone when the script check says Telugu, and use PSM 6 for single-column text. The strongest replacement is PaddleOCR PP-OCRv5's `te_PP-OCRv5_mobile_rec`. It is Apache-2.0, scores **87.65% Telugu line accuracy** ([PP-OCRv5 multilingual](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.en.md)), and its ONNX file is about 7.6 MiB ([oar-ocr](https://github.com/GreatV/oar-ocr/blob/main/docs/models.md)). An Apache-2.0 Android port already runs PP-OCRv5 on LiteRT with GPU and XNNPACK, but publishes no timings ([PPOCRv5-Android](https://github.com/iFleey/PPOCRv5-Android)).

AI Hub's EasyOCR gives a proxy for what a CRAFT/CRNN-style detector-recognizer costs on this NPU: **4.5 ms detector (w8a8) and 7.9 ms recognizer** on 8 Elite Gen 5 (P) ([HF EasyOCR](https://huggingface.co/qualcomm/EasyOCR)). The exported language is not stated. EasyOCR also ships a `telugu_g2` model ([EasyOCR Model Hub](https://www.jaided.ai/easyocr/modelhub/)). By analogy, a Paddle Telugu page should cost tens to low hundreds of milliseconds, against seconds for Tesseract. That is an estimate and unverified. Recognizers run per text line, so dense pages cost more. PP-OCRv6 claims its tiny tier is 3.9x faster than v5 mobile on a Xeon, but its Telugu coverage and model licence are **unconfirmed** ([arXiv 2606.13108](https://arxiv.org/pdf/2606.13108)). The architecture follows from these costs. Pass 1 runs gate, single-recognizer ML Kit and FTS insert, so documents become keyword-searchable immediately. Pass 2 runs Telugu or Devanagari OCR, full-resolution re-OCR of low-confidence pages and Nomic chunk embedding, under idle or charging constraints.

## Metadata ordering surfaces documents in the first minute

The scanner already does incremental rescans correctly: it tracks `GENERATION_MODIFIED` against a stored watermark and runs a full resync when `MediaStore.getVersion` changes, as AOSP prescribes ([MediaStore.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/apex/framework/java/android/provider/MediaStore.java)). Two gaps remain.

**Queue order.** The pending queue is read `ORDER BY generation ASC`, so a first run works **oldest photo first**, and documents appear in whatever order they were taken. The only public composition data is small: in a 5,000-image, 12-person 2019 study, **one in four** phone images was a screenshot ([The Conversation](https://theconversation.com/i-studied-5-000-phone-images-objects-were-more-popular-than-people-but-women-took-way-more-selfies-150080)). No study measures the share of documents or where they live. The hypothesis worth testing is that most documents sit in a minority of folders: Screenshots, Download, Documents, WhatsApp Images and WhatsApp Documents, `IS_DOWNLOAD=1`, and scanner-app `OWNER_PACKAGE_NAME`. Processing those tiers newest first, then A4- or ID-card-aspect camera photos, then the rest, should surface most documents within the first 10-25% of scan time (E).

**Pre-filters.** The cursor projection lacks `SIZE`, `WIDTH`, `HEIGHT`, `ORIENTATION` and `IS_DOWNLOAD`, so free pre-filters are impossible today ([MediaColumns](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns)). With them the scanner can drop GIFs, sticker WebPs, images under ~300 px, and trashed or pending items with zero file I/O. It can also classify one frame per burst and pick sample sizes without opening files. Treat NULL dimensions as "unknown", not as "drop". On a version reset, the scanner's own comment says "SHA-256 dedup keeps that cheap". It does not. Non-documents store no hash, so every photo is re-gated. Keying cached verdicts on `_ID + SIZE + DATE_MODIFIED` would make a reset cost one cursor walk. On Android 14+, a user who grants only partial photo access exposes only a subset of the gallery to the query ([shared storage](https://developer.android.com/training/data-storage/shared/media)).

## Android 16 needs a foreground mediaProcessing service

`IndexWorker` never calls `setForeground`, and the manifest declares no foreground service type. The worker is therefore a regular job capped at **10 minutes** ([long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)). At today's 3-8 photos/s, that cap bites for any gallery larger than about 2,000-5,000 photos. Resume works, because in-flight rows stay pending, but each stop costs a reschedule. A foreground service fixes this:

- **Type and manifest.** Call `setForeground(ForegroundInfo(id, notification, FOREGROUND_SERVICE_TYPE_MEDIA_PROCESSING))` at the top of `doWork()`. Declare `FOREGROUND_SERVICE_MEDIA_PROCESSING`, and merge `foregroundServiceType="mediaProcessing"` onto WorkManager's `SystemForegroundService`, which Android 14+ requires ([long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)). The type is available to apps targeting Android 15+; this app targets 37.
- **Time budget.** The type allows **6 hours per 24**, and the timer resets whenever the user returns to the app ([FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types); [FGS timeout](https://developer.android.com/develop/background-work/services/fgs/timeout)).
- **Start conditions.** Start it from the UI. Apps cannot start foreground services from the background ([background start](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)). `setForeground` can throw, so wrap it ([define work](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)).
- **Expedited work.** Expedited work is meant for tasks that finish "within a few minutes". It suits the content-URI "new photos" job, not the full index ([define work](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)).
- **Android 16 quota.** Android 16 adds a runtime quota. Jobs "executing concurrently with a foreground service" count against it, as do jobs that started visible and continued after the app left the screen. Google's advice when long-running workers exhaust it is to "try launching the foreground service directly" ([Android 16 changes](https://developer.android.com/about/versions/16/behavior-changes-all); [long-running workers](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)). If `WorkInfo.getStopReason()` shows quota stops on OriginOS 6, move the bulk pass to a plain `Service` of type `mediaProcessing` that implements `onTimeout`.

Even a correctly configured foreground service runs slower off-screen. AOSP assigns cpusets by importance, and background tasks are "packed" onto few CPUs ([AOSP jank capacity](https://source.android.com/docs/core/tests/debug/jank_capacity); [LWN](https://lwn.net/Articles/706374/)). A foreground service keeps the process out of the cached-app freezer, which otherwise freezes cached apps after 10 s ([cached apps freezer](https://source.android.com/docs/core/perf/cached-apps-freezer)). It does not grant top-app CPU priority. The iQOO 15's actual cpuset map is unknown. Decoder count should follow visibility, for example four decoders on screen and two off screen. For the evaluation, keep the app visible with the screen held on.

vivo rates 3/5 on dontkillmyapp. The site lists "no known solution on dev end". Users must enable "High background power consumption", Autostart and Recents lock by hand ([dontkillmyapp vivo](https://dontkillmyapp.com/vivo)). An onboarding checklist is the only lever. Google Play restricts direct battery-exemption requests, which matters only if the app is published there ([Doze](https://developer.android.com/training/monitoring-device-state/doze-standby)).

## Conclusion

The research changes where the effort should go. The evaluation will probably expect "use the NPU harder": quantise, batch, swap in a smaller CLIP. On this chip the NPU finishes its part in about 3 ms and then waits on the CPU. The real gains come from decoding less, which follows from how Skia picks sample sizes, and from overlapping stages, which follows from the core count. OCR structure matters most once decode is fixed, because 10% documents at 300 ms each caps the whole gallery at about 33 photos/s. Two consequences are less obvious. First, "photos/second" should be reported as two numbers: gate throughput, and time until documents become searchable. The two-pass design optimises the second without sacrificing the first. Second, the only change that could make the pipeline catastrophically slow is not a tuning choice but a silent CPU fallback. A single log assertion is worth more than all the NPU tuning combined.

Three results would change these rankings. If ML Kit on this device is far faster than assumed, say under 50 ms per page, OCR stops being the ceiling and the decode pool dominates. If `loadThumbnail` cache hits land under 5 ms and OriginOS's own gallery has already populated the cache, the thumbnail route beats sample-8 decoding outright. If quota stops appear on OriginOS 6 even with a foreground service, the WorkManager architecture itself needs replacing. The measurements below settle all three.
