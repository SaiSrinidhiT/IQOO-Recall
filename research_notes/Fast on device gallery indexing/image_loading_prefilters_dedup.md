# Fast on-device gallery indexing: image loading, zero-cost pre-filters, dedup and ordering (Android 11-16, iQOO 15 / SM8850)

Scope note: most "how it works" findings below come from reading AOSP / Skia source directly (GitHub mirrors of `main` fetched Sept 2026). MediaProvider is a Mainline module, so the exact code on an iQOO 15 (OriginOS 6 / Android 16) depends on its MediaProvider module version, but the thumbnail and decode paths quoted have been stable since Android 10/11 (the Android 11 `ThumbnailUtils` branch has the same logic). **I found no published, device-measured per-image millisecond benchmarks for loadThumbnail / ImageDecoder / BitmapFactory on Snapdragon 8-series phones.** Every ms figure below that is not tied to a source is an explicitly labelled ESTIMATE derived from cited throughput numbers; the report writer should present them as estimates and recommend on-device measurement (e.g. Macrobenchmark / `Trace` sections — hwui already emits `ATRACE` markers like "getAndroidPixels" and "Handling scale/origin/crop").

Target device facts: iQOO 15 has a 6.85" 3168x1440 AMOLED, Snapdragon 8 Elite Gen 5, UFS 4.1, 12/16 GB RAM, OriginOS 6 on Android 16; main camera is 50 MP Sony IMX921 — [iQOO India store](https://shop.iqoo.com/in/product/2067). (50 MP sensors normally output ~12.5 MP binned 4080x3072-class JPEG/HEIC by default — common industry behaviour, not verified for this model.)

## 1. ContentResolver.loadThumbnail(uri, Size, signal): internals, latency, caveats

### Takeaway
`loadThumbnail` is a binder call into MediaProvider that returns a **persistent on-disk JPEG thumbnail cache** (`Pictures/.thumbnails/<_ID>.jpg`) sized to **half the device's smallest screen edge regardless of the Size you ask for**; on a cache miss MediaProvider generates it synchronously (HEIF embedded thumbnail → EXIF embedded thumbnail → full ImageDecoder decode), JPEG-encodes it at q90 and writes it. Cached hits should be the cheapest possible path to a ~256 px bitmap (small file + small decode); first-run cost for PNG screenshots and JPEGs without an EXIF thumbnail is essentially "full decode + JPEG encode + write" done inside MediaProvider's process.

### Cited Findings
- **Client side (framework):** `ContentResolver.loadThumbnail` puts the requested size in `EXTRA_SIZE` (as a `Point`) and calls `openTypedAssetFile(uri, "image/*", opts, signal)`, then decodes the returned FD with `ImageDecoder`. In `onHeaderDecoded` it computes `sample = max(srcW / reqW, srcH / reqH)` (integer division) and calls `setTargetSampleSize(sample)` only if `sample > 1` — comment: "We requested a rough thumbnail size, but the remote size may have returned something giant, so defensively scale down as needed." Rotation is applied afterwards with a `Matrix` via an `EXTRA_ORIENTATION` side-channel "since EXIF thumbnails don't contain the rotation flags of the original image." — [AOSP ContentResolver.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/core/java/android/content/ContentResolver.java)
- **Provider side:** `openTypedAssetFileCommon` treats a request as a thumbnail request when `opts` contains `EXTRA_SIZE` and the MIME filter starts with `image/`; it then calls `ensureThumbnail(uri, signal)` and returns that FD ("Offer thumbnail of media, when requested"); otherwise "Worst case, return the underlying file". — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)
- **The requested Size is ignored for generation:** MediaProvider's thumbnail size is fixed at start-up: "Reasonable thumbnail size is half of the smallest screen edge width" → `thumbSize = min(widthPixels, heightPixels) / 2; mThumbSize = new Size(thumbSize, thumbSize)`; all image thumbnails are generated with `ThumbnailUtils.createImageThumbnail(file, mThumbSize, signal)`. — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)
- **Cache location / format:** `getThumbnailFile` = `<primary external volume>/Pictures/.thumbnails/<_ID>.jpg` ("Always save generated thumbnails to primary storage"). `ensureThumbnail` "First attempt[s] to fast-path by opening the thumbnail"; on miss it creates a temp file, calls `getThumbnailBitmap`, `thumbnail.compress(Bitmap.CompressFormat.JPEG, 90, ...)`, then renames into place; concurrent requests for the same ID may both generate (no per-ID lock, by design). — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)
- **Invalidation:** thumbnails are deleted when the item is updated/deleted (`invalidateThumbnails`), stale ones are pruned against known IDs during maintenance, and if the database UUID stored on disk disagrees with the DB, MediaProvider logs "Invalidating all thumbnails under <dir>" and wipes the directory. — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)
- **Generation order in `ThumbnailUtils.createImageThumbnail(File, Size, signal)`:** (1) read EXIF orientation for EXIF-capable MIME types; (2) for `image/heif`, `heif-sequence`, `heic`, `heic-sequence`, `avif`: `MediaMetadataRetriever.getThumbnailImageAtIndex(-1, params, size.getWidth(), size.getWidth()*size.getHeight())`; (3) if still null and EXIF present: `exif.getThumbnailBytes()` decoded with ImageDecoder — **no minimum-size check on the EXIF thumbnail**; (4) otherwise `ImageDecoder.decodeBitmap(createSource(file), resizer)` (full-file decode). Same logic in the android11-release branch. — [AOSP ThumbnailUtils.java (main)](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/media/java/android/media/ThumbnailUtils.java), [android11-release](https://github.com/aosp-mirror/platform_frameworks_base/blob/android11-release/media/java/android/media/ThumbnailUtils.java)
- The `Resizer` used there forces `ALLOCATOR_SOFTWARE` and applies the same integer `setTargetSampleSize(max(w/W, h/H))` rule, so generated thumbnails are between ~1x and ~2x `mThumbSize` on the long edge. — [AOSP ThumbnailUtils.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/media/java/android/media/ThumbnailUtils.java)
- HEIF path heuristic: `getThumbnailImageAtIndex(imageIndex, params, targetSize, maxPixels)` (a `@hide` API) "retrieves the thumbnail image for a still image if it's available"; `targetSize` "is a heuristic for the framework to decide whether the embedded thumbnail should be used" and `maxPixels` decides "whether the embedded thumbnail (or a downscaled version of it) should be used". — [AOSP MediaMetadataRetriever.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/media/java/android/media/MediaMetadataRetriever.java)
- Android docs recommend `loadThumbnail()` "passing in the size of the thumbnail you want" when showing many media items instead of loading the files themselves. — [Access media files from shared storage](https://developer.android.com/training/data-storage/shared/media)
- Fresco maintainers/users proposed `loadThumbnail` as a faster path than MediaMetadataRetriever for video thumbnails (no timings given). — [Fresco issue #2767](https://github.com/facebook/fresco/issues/2767)
- iQOO 15 panel is 3168x1440 — [iQOO store](https://shop.iqoo.com/in/product/2067) — so at native resolution `mThumbSize` = 720x720; if OriginOS is set to an FHD+ render mode (1080 wide, common default on vivo/iQOO — unverified), `mThumbSize` = 540x540.

### Inferences
- **Output size for Size(256,256):** with a 720 px cached thumb of a 4:3 photo (e.g. 960x720 or 720x540 depending on source sampling), client-side sample = 720/256 = 2 → returned bitmap ≈ 360-480 px long edge, not 256. You still need a final `Bitmap.createScaledBitmap`/crop to 224 (cheap, <1 ms class for ~400 px). Aspect ratio is preserved (no square crop).
- **Quality caveat (important for documents):** for camera JPEGs that carry an EXIF thumbnail, MediaProvider will store *that* thumbnail (commonly 160x120 to 512x384 px on phones — typical values, not verified for vivo/iQOO) re-encoded at q90, even though `mThumbSize` is 720. For a 224x224 SigLIP2 "is this a document?" gate that is probably adequate; for anything text-legible it is not. Some EXIF thumbnails are fixed 4:3 or 16:9 with letterboxing for other aspect ratios (unverified), which could slightly bias the classifier.
- **Latency (ESTIMATES, no source):** cache hit = binder IPC + open of a ~20-80 KB JPEG + decode at 1/2 sample → roughly 2-8 ms per image on a flagship; cache miss with EXIF thumbnail = EXIF parse + small decode + JPEG encode + write → roughly 5-15 ms; cache miss requiring full decode (PNG screenshots, HEIC without usable embedded thumb, JPEG without EXIF thumb) = same full-decode cost as doing it yourself (tens to 100+ ms for 12 MP) plus JPEG encode and a file write, executed in MediaProvider's process (serialised through its binder threads). Measure on device.
- **First-run cost / side effects:** a whole-gallery scan through `loadThumbnail` will *populate* `Pictures/.thumbnails` for every image (disk writes of ~20-80 KB each, i.e. roughly 0.2-0.8 GB for 10k photos — estimate), which then benefits every later rescan and other apps. vivo's own Gallery app very likely uses its own private cache rather than MediaProvider's, so on first run of your app most entries are probably uncached (unverified).
- Because the requested Size is ignored for generation, requesting 256 vs 512 does not change first-run cost, only the client-side sample.
- Because orientation is applied client-side via `Bitmap.createBitmap(..., matrix)`, rotated photos incur one extra bitmap copy (small at thumbnail size).
- For concurrency, calling `loadThumbnail` from many threads helps only up to MediaProvider's binder thread pool (typically 16-31 threads in system providers — unverified) and CPU cores.

### Gaps
- No published measured ms for `loadThumbnail` cached vs uncached on any Snapdragon device; no data on what fraction of MediaProvider thumbnails are already cached on a typical vivo/iQOO phone.
- Could not verify OriginOS's default display resolution mode (affects 540 vs 720 thumb size) or whether vivo modified MediaProvider thumbnail logic.
- Could not confirm the HEIF embedded-thumbnail dimensions vivo/iQOO cameras write (determines whether the HEIF fast path is taken).

## 2. ImageDecoder.setTargetSize vs BitmapFactory.inSampleSize; JPEG DCT-domain downscaling; RGB_565 / HARDWARE

### Takeaway
Android's ImageDecoder/BitmapFactory sit on Skia's `SkAndroidCodec`, which **does** use libjpeg-turbo IDCT scaling — but only when the chosen integer sample size is 2, 4, 8 or a multiple of them. `setTargetSize` picks the *largest-that-is-not-too-small* integer sample, which for typical phone photos to ~256 px frequently lands on an odd sample (e.g. 15) and **silently loses DCT scaling**; and when the target is not an exact sampled size, hwui first decodes into a **full-decode-size temporary heap bitmap** and then canvas-scales. The current pipeline's `setTargetSize(longest ≤ 2048)` on a 4080x3072 photo computes sample size 1: i.e. a full 12.5 MP decode into a ~50 MB temp buffer plus a 12.6 MB output, for every photo. Requesting an explicit 1/8 decode (`setTargetSampleSize(8)` / `inSampleSize = 8`) should be the single biggest decode win for the 224 px gate.

### Cited Findings
- hwui `ImageDecoder::setTargetSize(w,h)` calls `mCodec->computeSampleSize(&decodeSize)`, stores `mOptions.fSampleSize = sampleSize`, `mDecodeSize = decodeSize`, `mTargetSize = targetSize`. — [AOSP hwui ImageDecoder.cpp](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/libs/hwui/hwui/ImageDecoder.cpp)
- In `decode`, if `mDecodeSize != mTargetSize` (or EXIF origin/crop handling is needed) it allocates a temporary `SkBitmap tmp` of the decode size with `Bitmap::allocateHeapBitmap(&tmp)` ("Used if we need a temporary before scaling or subsetting. FIXME: Use scanline decoding on only a couple lines to save memory. b/70709380"), decodes into it via `getAndroidPixels`, then draws it into the output with `SkSamplingOptions(SkFilterMode::kLinear)` ("Handling scale/origin/crop"). — [AOSP hwui ImageDecoder.cpp](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/libs/hwui/hwui/ImageDecoder.cpp)
- `SkAndroidCodec::computeSampleSize`: `sampleX = origW / desiredW; sampleY = origH / desiredH; sampleSize = min(sampleX, sampleY)`; if the sampled size is strictly bigger than desired it tries `sampleSize + 1`, stopping when the result would be smaller than desired in either dimension. Animated WebP can't be downscaled. — [Skia SkAndroidCodec.cpp](https://github.com/google/skia/blob/main/src/codec/SkAndroidCodec.cpp)
- `SkSampledCodec::accountForNativeScaling`: "Only JPEG supports native downsampling." Sample sizes 2, 4, 8 map directly to libjpeg scale factors; otherwise it checks whether the sample size is a multiple of 8, 4 or 2 and uses that native scale followed by Skia sampling; any other sample size gets no native scaling. — [Skia SkSampledCodec.cpp](https://github.com/google/skia/blob/main/src/codec/SkSampledCodec.cpp)
- `SkJpegCodec::onDimensionsSupported`: "libjpeg-turbo can scale to 1/8, 1/4, 3/8, 1/2, 5/8, 3/4, 7/8, and 1/1" and sets `scale_num/scale_denom` accordingly. — [Skia SkJpegCodec.cpp](https://github.com/google/skia/blob/main/src/codec/SkJpegCodec.cpp)
- libjpeg-turbo IDCT scaling: only 1/2 and 1/4 (plus 1/8 per Mozilla's usage) are SIMD-accelerated among the many supported factors. Mozilla measured (desktop, `giant-map.jpg` 4992x4272): IDCT-scaled decode + Lanczos3 vs full decode + Lanczos3 = **1.76-1.78x faster at 1/2, 2.02-2.04x at 1/4, 2.36-2.38x at 1/8**; peak RSS **3.3-3.5x lower at 1/2, 9.9-10.5x at 1/4, 20.2-20.5x at 1/8** ("a 1/8 IDCT step cuts the buffer to 1/64 the full-decode size"). — [Mozilla bug 2033250](https://bugzilla.mozilla.org/show_bug.cgi?id=2033250) (x86 desktop, not ARM; speedup is bounded because Huffman/entropy decoding of all coefficients is still required)
- libjpeg-turbo's published performance report is for v1.5.x and gives only relative figures: Armv8 decompression 1.76-2.59x faster than libjpeg v6b; the authors note 2.0/2.1 improved performance significantly. — [libjpeg-turbo Performance](https://libjpeg-turbo.org/About/Performance)
- Order-of-magnitude libjpeg-turbo throughput on a modern ARM64 core: ~1,000 ImageNet images/s (avg 130 KB, typical ~500x400) with OpenCV/torchvision/kornia-rs on Apple M4 Max. — [arXiv 2501.13131](https://arxiv.org/html/2501.13131v1) (desktop ARM, small images; not a phone)
- Android docs: a 2048x1536 image decoded with `inSampleSize = 4` yields ~512x384, using 0.75 MB instead of 12 MB (ARGB_8888). — [Loading Large Bitmaps Efficiently](https://developer.android.com/topic/performance/graphics/load-bitmap)
- HEIC: Android 10+ supports HEIC via HEVC hardware; HEIF can store tiles and embedded thumbnails. — [AOSP HEIF imaging](https://source.android.com/docs/core/camera/heif). Glide users report HEIF/HEIC galleries loading "so SLOW" / freezing on Samsung and Pixel devices (no timings). — [Glide #4608](https://github.com/bumptech/glide/issues/4608) (anecdotal)
- The only Skia codec with native downsampling is JPEG; HEIF (`SkHeifCodec`), PNG and WebP decode at full resolution and then subsample. — [Skia SkSampledCodec.cpp](https://github.com/google/skia/blob/main/src/codec/SkSampledCodec.cpp)

### Inferences
- **Worked examples from the Skia logic above (derived, not measured):**
  - Current code, 4080x3072 JPEG, target 2048x1536: `sampleX = 4080/2048 = 1` → sample 1 → full 12.5 MP IDCT into a 4080x3072x4 B ≈ **50 MB temp** + **12.6 MB** 2048x1536 output + the ~3-8 MB `readBytes` array ≈ **65-70 MB transient per image**, then the 2048 bitmap is thrown away for 90%+ of photos.
  - 4080x3072 JPEG, `setTargetSize(256,192)`: `sampleX = 15, sampleY = 16` → min 15 → 272x204 strictly bigger → try 16 → native 1/8 (510x384) then /2 → 255x192 is smaller than 256 → stops at **15 → no DCT scaling** (15 isn't a multiple of 2/4/8); full-resolution IDCT with Skia row/column sub-sampling, then a temp 272x204 + linear scale to 256x192.
  - `setTargetSampleSize(8)` (or `setTargetSize(ceil(w/8), ceil(h/8))`, or `BitmapFactory` `inSampleSize = 8`) on the same file → libjpeg 1/8 IDCT → 510x384 output, 0.78 MB, no temp buffer; then scale/crop to 224 yourself (or `inSampleSize = 16` → 1/8 native + 2x sampling → 255x192).
  - 50 MP full-res 8160x6144 JPEG with target 2048: sample 3 → no native scaling either.
- **Recommended decode for the 224 gate:** read `WIDTH/HEIGHT` from MediaStore (or `onHeaderDecoded` `info.size`), choose the largest power-of-two sample `s ∈ {8, 4, 2}` such that the short side stays ≥ 224-256, call `decoder.setTargetSampleSize(s)` (not `setTargetSize`), `ALLOCATOR_SOFTWARE`, `setMemorySizePolicy(MEMORY_POLICY_LOW_RAM)` optional, then one `createScaledBitmap` to 224. For a 4080x3072 photo s = 8 → 510x384 (short side 384 ≥ 224).
- **Estimated timings (ESTIMATES, derive from Mozilla ratios; measure on device):** if a full 12.5 MP JPEG decode on an Oryon prime/perf core is ~40-100 ms (assumes ~125-300 MP/s single-thread libjpeg-turbo on a 2025 flagship core — unverified), then 1/8 decode would be ~15-45 ms (≥2.4x faster per Mozilla, likely more on ARM because the full-size canvas scale step also disappears), and memory drops ~64x for the pixel buffer.
- **HEIC:** no DCT-style shortcut; ImageDecoder decodes the full primary image via the HEVC hardware decoder (tiles) and subsamples. The fast path is the **embedded HEIF thumbnail**, which apps can reach via public `ThumbnailUtils.createImageThumbnail(File, Size, signal)` (API 29; needs a real file path, which READ_MEDIA_IMAGES + FUSE allows on API 30+) or via `loadThumbnail` (which uses it on cache miss). `MediaMetadataRetriever.getThumbnailImageAtIndex` itself is `@hide`.
- **PNG screenshots** (no DCT scaling, no EXIF thumb): full inflate is unavoidable; 1440x3168 PNG decode is ~4.6 MP — estimate 20-60 ms. `loadThumbnail` caching helps on rescans only.
- **RGB_565:** halves bitmap bytes but gives no decode-time win for JPEG in practice (libjpeg-turbo's cost is entropy + IDCT) and must be converted back to RGB float tensors for SigLIP2; not worth it at 224 px. **HARDWARE bitmaps:** pixels live in GPU memory; CPU access (`copyPixelsToBuffer`, `getPixels`) is not allowed without a `copy(ARGB_8888)`, so they are a poor fit for feeding a CPU/NPU tensor — keep `ALLOCATOR_SOFTWARE`.
- **Ultra HDR JPEGs** (gainmap): on Android 14+ ImageDecoder may also decode the gainmap (hwui has `extractGainmap`) — extra cost you don't need for classification; worth checking with a trace (unverified whether it runs on sampled decodes).
- `BitmapFactory` in modern Android is also built on `SkAndroidCodec`, so `inSampleSize = 8` should hit the same native 1/8 path (inferred from shared Skia code path; BitmapFactory.cpp not inspected in this session). Android docs historically say non-power-of-2 values are rounded down; Skia actually honours arbitrary values but only multiples of 2/4/8 get DCT scaling.

### Gaps
- No device-measured ms for ImageDecoder/BitmapFactory at 1/1, 1/4, 1/8 on Snapdragon 8 Elite (Gen 1 or Gen 5), nor for HEIC decode via hardware HEVC on these SoCs. Recommend a 30-minute on-device microbenchmark with ~50 representative files.
- Could not verify whether libjpeg-turbo 1/8 scaling is NEON-accelerated on Android's bundled libjpeg-turbo build (Mozilla says 1/8 path is SIMD; libjpeg-turbo README lists only 1/2 and 1/4 as SIMD — sources disagree slightly).

## 3. ExifInterface.getThumbnailBitmap / embedded thumbnail

### Takeaway
Reading the EXIF thumbnail is the fastest source of pixels for camera JPEGs (only the header region is read, a tiny JPEG is decoded), and MediaProvider itself uses it; but it is absent from PNG screenshots and many edited/re-encoded/messaging-app images, and its resolution is low. I found no published availability-rate statistics.

### Cited Findings
- AOSP thumbnail generation prefers `exif.getThumbnailBytes()` for EXIF-capable MIME types (JPEG etc.) before full decoding, and applies EXIF orientation to it manually because the thumbnail isn't pre-rotated. — [AOSP ThumbnailUtils.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/media/java/android/media/ThumbnailUtils.java)
- `ContentResolver.loadThumbnail` notes "EXIF thumbnails don't contain the rotation flags of the original image." — [AOSP ContentResolver.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/main/core/java/android/content/ContentResolver.java)
- Legacy MediaStore thumbnail kinds were MINI_KIND 512x384 and MICRO_KIND 96x96 (historical reference for "thumbnail" sizes). — [MediaStore.Images.Thumbnails](https://developer.android.com/reference/android/provider/MediaStore.Images.Thumbnails)
- HEIF containers can embed thumbnail images for quick display. — [AOSP HEIF imaging](https://source.android.com/docs/core/camera/heif)

### Inferences
- Availability (unverified, from general knowledge): most OEM camera JPEGs include an EXIF IFD1 thumbnail (typically 160x120 to 512x384); PNG screenshots have none; WhatsApp/Telegram-received images and many editor exports strip EXIF (so no thumbnail); WebP stickers have none. Expect high availability for DCIM/Camera JPEGs and low elsewhere — which is roughly the inverse of where documents live (Screenshots, WhatsApp, Downloads).
- Speed (ESTIMATE): androidx `ExifInterface` on a FileDescriptor/InputStream parses only the APP1 segment (typically < 64 KB); decoding a ~10-30 KB thumbnail at ≤512 px is ~1-3 ms; total ~2-5 ms/image. Use `ExifInterface(fd)` with `hasThumbnail()`/`getThumbnailBytes()` and decode bytes with `ImageDecoder.createSource(ByteBuffer)`; check thumbnail dimensions (`getThumbnailRange`/decoded size) and fall back to a 1/8 decode if the short side < ~160 px.
- Rotation must be applied (EXIF ORIENTATION / MediaStore ORIENTATION column).
- For a combined strategy, `loadThumbnail` already implements "HEIF thumb → EXIF thumb → full decode" and persists the result, so a hand-rolled EXIF path mainly helps if MediaProvider round-trips are slower than expected on this device.

### Gaps
- No source found giving the % of modern Android camera photos (incl. vivo/iQOO, HEIC mode) that carry an EXIF or HEIF thumbnail, or its typical size.
- No measured ms for `ExifInterface.getThumbnailBitmap` on flagship phones.

## 4. Zero-cost pre-filtering with MediaStore metadata; gallery composition data

### Takeaway
A single MediaStore query can return size, dimensions, MIME type, folder, dates, favourites, orientation, download flag, owner package and generation counters for every image without opening a file; use it to drop stickers/GIFs/tiny images/bursts cheaply and to push Screenshots, Download(s), WhatsApp Images/Documents and portrait-aspect images to the front. The only public composition data found says ~1 in 4 phone images is a screenshot (small 2019 study); I found no statistic for the fraction that are documents.

### Cited Findings
- `MediaStore.MediaColumns` exposes WIDTH, HEIGHT, SIZE, MIME_TYPE, RELATIVE_PATH, BUCKET_DISPLAY_NAME, DATE_TAKEN, DATE_MODIFIED, IS_FAVORITE, ORIENTATION, IS_DOWNLOAD, IS_PENDING, IS_TRASHED (API 30), OWNER_PACKAGE_NAME, XMP, RESOLUTION, GENERATION_ADDED/GENERATION_MODIFIED. — [MediaStore.MediaColumns reference](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns) (API levels as summarised by the fetch tool; minSdk 30 makes them all available regardless)
- GENERATION_MODIFIED: "Generation number at which metadata for this media item was last changed. This is useful for apps that are attempting to quickly identify exactly which media items have changed since a previous point in time. Generation numbers are monotonically increasing ... can be safely arithmetically compared"; more robust than DATE_MODIFIED "since those values may change in unexpected ways when apps use File#setLastModified(long) or when the system clock is set incorrectly." — [AOSP MediaStore.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/apex/framework/java/android/provider/MediaStore.java)
- Study of ~5,000 phone images from 12 people in Australia (four weeks, early 2019): "one in four images" was a screenshot; per four images ~1.74 were objects, 1.07 humans, 1.0 environment, 0.18 animals; only 6.5% were shared on social media. — [The Conversation](https://theconversation.com/i-studied-5-000-phone-images-objects-were-more-popular-than-people-but-women-took-way-more-selfies-150080) (small, non-representative sample)
- Android 14+ partial media access (user-selected photos) means a MediaStore query may only see a subset of the gallery — see [Access media files from shared storage](https://developer.android.com/training/data-storage/shared/media).

### Inferences
- **Pre-filter rules (all from the cursor, 0 file I/O):**
  - Drop `MIME_TYPE` in {image/gif, image/webp from `.../WhatsApp Stickers/` or `RELATIVE_PATH` containing "Stickers"}, and anything with `min(WIDTH, HEIGHT) < ~300 px` or `SIZE < ~20 KB` (emoji, icons, avatars). Keep small WebP outside sticker folders.
  - Skip `IS_TRASHED=1`, `IS_PENDING=1`.
  - WIDTH/HEIGHT can be 0/NULL for some files (not yet scanned) — treat as "unknown", don't drop.
  - Apply ORIENTATION to decide portrait vs landscape (WIDTH/HEIGHT are stored pre-rotation for JPEGs, so swap when ORIENTATION is 90/270).
  - Bursts: group by BUCKET_ID + DATE_TAKEN within ~1 s and identical WIDTH/HEIGHT; classify only the first frame, propagate the result (heuristic).
- **Priority tiers (heuristic):** (1) `RELATIVE_PATH` matches `Pictures/Screenshots/`, `DCIM/Screenshots/`, `Download/`, `Documents/`, `Android/media/com.whatsapp/WhatsApp/Media/WhatsApp Documents/` and `.../WhatsApp Images/`, Telegram, scanner apps (via OWNER_PACKAGE_NAME), `IS_DOWNLOAD=1`; (2) portrait aspect near A4 (1:1.41), letter (1:1.29) or ID-card landscape (1.58:1) in DCIM/Camera; (3) everything else. `IS_FAVORITE` is a weak signal only.
- Given "1 in 4 images is a screenshot" and that documents are typically <10% of a gallery (per the task's own observation), tier-1 folders may contain most documents while being a minority of files, so folder-first ordering should surface most documents in the first fraction of scan time (hypothesis to validate on real galleries).
- Querying ~10k rows with a narrow projection is a single IPC-backed cursor walk; expected tens of ms (ESTIMATE); page with `QUERY_ARG_LIMIT`/`OFFSET` via `Bundle` query args if needed.

### Gaps
- No published data on the fraction of a typical Android gallery that is documents / IDs / bills, nor on screenshots specifically for Indian users or WhatsApp-heavy galleries.
- Could not verify vivo/OriginOS screenshot folder name and format (PNG vs JPEG) on the iQOO 15.

## 5. Faster exact / near-duplicate detection; SHA-256 and storage read costs

### Takeaway
SHA-256 itself is cheap on ARMv8 with crypto extensions (~2 cycles/byte → roughly 1.5-2.5 GB/s per core, i.e. a few ms per photo), and UFS 4.x sequential reads are ~4 GB/s, so the hashing is not the dominant cost — the dominant costs are allocating/reading the full file into a Java `byte[]` for every image and then the full-resolution decode. Replace "whole-file SHA-256 up front" with a MediaStore-key cache (_ID + SIZE + DATE_MODIFIED/GENERATION_MODIFIED) plus a cheap partial hash for exact dups, and a perceptual dHash on the 224-256 px bitmap for near dups; only hash full bytes for likely documents if needed.

### Cited Findings
- OpenSSL's ARMv8 SHA-256 with crypto extensions (`SHA256-hw`): 1.97 cycles/byte (Apple A7), 2.38 (Cortex-A53), 2.31 (Cortex-A57), 1.92 (Qualcomm Kryo), 2.36 (Mongoose), 2.54 (ThunderX2); software SHA-256 is 10.5-17.4 cycles/byte. — [OpenSSL sha512-armv8.pl header](https://github.com/openssl/openssl/blob/master/crypto/sha/asm/sha512-armv8.pl) (older cores; no Oryon/Cortex-X figures found)
- Samsung UFS 4.0: up to 4,200 MB/s sequential read, 2,800 MB/s sequential write. — [Samsung Semiconductor UFS 4.0](https://semiconductor.samsung.com/estorage/ufs/ufs-4-0/); iQOO 15 uses UFS 4.1 — [iQOO store](https://shop.iqoo.com/in/product/2067)
- FUSE can reduce bandwidth vs direct lower-filesystem access, "especially with random read operations"; FUSE passthrough exists from Android 12 (android12-5.4/5.10+ kernels) and the FUSE daemon decides per file whether passthrough is used. — [AOSP FUSE passthrough](https://source.android.com/docs/core/storage/fuse-passthrough)
- **MediaProvider open path:** when the caller needs location redaction, MediaProvider returns an FD "that points to the fuse file system and handle[s] redaction in the fuse handler when the caller reads" (`openWithFuse(..., shouldRedact=true)`); otherwise it opens the lower filesystem directly (logging "Open with lower FS for <path>") unless the file is already open via FUSE with VFS caching. Opening the original unredacted file requires `ACCESS_MEDIA_LOCATION`. — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)

### Inferences
- **Current cost per photo (ESTIMATE):** a 5-10 MB file at ~1.5-3 GB/s effective read ≈ 2-7 ms; SHA-256 at ~2 cycles/byte on a ~4 GHz core ≈ 2 GB/s → 2.5-5 ms; Java `readBytes` allocates a fresh multi-MB `byte[]` per image (GC churn in the large-object space). For 10,000 photos × 6 MB ≈ 60 GB read + hashed ≈ roughly 1 minute of I/O+hash total — noticeable but much smaller than decoding 10,000 full-res images at tens of ms each (~5-15+ min single-threaded).
- Android's default `MessageDigest.getInstance("SHA-256")` provider is Conscrypt/BoringSSL, which uses ARMv8 SHA instructions (general knowledge; not verified in this session). Hashing incrementally from a stream with a 64-256 KB reusable buffer avoids the `byte[]` allocation entirely.
- **Redaction trap:** if the app lacks `ACCESS_MEDIA_LOCATION`, every GPS-tagged photo is served through the FUSE redaction path (userspace daemon per read), which is slower than a lower-fs FD and also means the bytes you hash are *redacted bytes*. Request `ACCESS_MEDIA_LOCATION` (and use `MediaStore.setRequireOriginal(uri)`) if you need original bytes/hashes; or avoid whole-file reads altogether.
- **Cheaper exact-dup keys:**
  1. Re-scan skip: `(_ID, SIZE, DATE_MODIFIED, GENERATION_MODIFIED)` unchanged ⇒ reuse previous result, zero I/O.
  2. Exact copies across folders (e.g. Download + WhatsApp copy): group candidates by `SIZE` (and WIDTH/HEIGHT/MIME) first — files of unique size cannot be exact duplicates; only hash within size-collision groups. Partial hash = SHA-256 or xxHash64 of (SIZE ‖ first 64 KB ‖ last 64 KB) ≈ 128 KB of I/O (<0.2 ms) — confirm with a full hash only on partial-hash collisions if exactness matters.
  3. Near dups (re-compressed WhatsApp copies, screenshots of the same doc, bursts): 64-bit dHash (resize to 9x8 grayscale, compare adjacent pixels) or pHash (32x32 DCT) computed from the already-decoded 224-256 px bitmap — microseconds of CPU; Hamming distance ≤ ~6-10 as "near duplicate" (thresholds from common practice, tune on data). SigLIP2 embeddings themselves also give near-dup detection via cosine similarity at no extra cost.
- Whole-byte exact dup detection rarely matters for documents: messaging apps re-encode, so true byte-identical copies are mostly file-manager copies (caught by SIZE grouping), while the common case (same doc, different bytes) needs perceptual/embedding similarity anyway.

### Gaps
- No SHA-256 throughput figure found for Oryon (SM8750/SM8850) or Cortex-X cores; ~2 cycles/byte is extrapolated from older ARMv8 cores.
- No measured MB/s for app-level ContentResolver reads on Android 16 (FUSE lower-fs vs redacted path) or random-read IOPS for UFS 4.1.

## 6. Ordering strategies and incremental scanning via GENERATION_MODIFIED

### Takeaway
Use a two-stage ordering: folder/signal priority tiers first (Screenshots, Download(s), WhatsApp Documents/Images, Documents, scanner-app owners), newest-first within each tier, then the camera roll newest-first; persist `MediaStore.getVersion(volume)` + the max `GENERATION_MODIFIED` seen and on later runs query only `GENERATION_MODIFIED > lastGen` (full resync if the version string changed).

### Cited Findings
- `MediaStore.getGeneration(Context, volumeName)` returns the volume's current generation; generation numbers are monotonic and more robust than DATE_ADDED/DATE_MODIFIED; "before comparing these detailed generation values, you should first confirm that the overall version hasn't changed by checking MediaStore#getVersion(Context, String) ... If the overall version changes, you should assume that generation numbers have been reset and perform a full synchronization pass." — [AOSP MediaStore.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/apex/framework/java/android/provider/MediaStore.java)
- `GENERATION_ADDED` marks when an item entered MediaStore; `GENERATION_MODIFIED` changes when the item's metadata changes. — [MediaStore.MediaColumns reference](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns)
- MediaProvider invalidates an item's cached thumbnail when the item is updated, so a changed item needs a fresh `loadThumbnail` (automatic). — [AOSP MediaProvider.java](https://github.com/aosp-mirror/platform_packages_providers_mediaprovider/blob/main/src/com/android/providers/media/MediaProvider.java)

### Inferences
- **Incremental loop:** store `(volumeName, version, lastGeneration)`; on start: if `getVersion` differs → full rescan (but reuse per-item results keyed on `_ID+SIZE+DATE_MODIFIED`); else query `GENERATION_MODIFIED > lastGeneration` (catches both new and modified rows, since new rows also get a generation) and separately detect deletions by diffing stored `_ID`s (or a `ContentObserver` for live updates). Update `lastGeneration = getGeneration()` read *before* the query to avoid missing concurrent changes.
- **Ordering within a pass:** process tier-1 folders newest-first (recent bills/IDs are most likely to be searched), then tier-2 portrait/aspect-matched camera photos, then the remainder newest-first. Emit results progressively so the UI can show documents while the tail is still scanning.
- **Pipeline shape to minimise per-image cost (derived from sections 1-5):** cursor pre-filter → skip if cached result for `(_ID, SIZE, DATE_MODIFIED)` → get 224-256 px pixels via (a) `loadThumbnail` (cached = fastest) or (b) EXIF/HEIF thumbnail or (c) JPEG `setTargetSampleSize(8)` decode → SigLIP2 gate + dHash → only for "document" hits: open full file, full-res decode for OCR, optional full SHA-256. Run decode on 3-4 worker threads (CPU-bound, per-image allocations now < 1 MB) feeding a single NPU inference queue.
- For "newest first" you can sort by `DATE_TAKEN DESC` (NULL for many screenshots/downloads) with fallback `DATE_ADDED DESC`; `DATE_MODIFIED` can be rewritten by apps.

### Gaps
- No published evaluation comparing folder-priority vs recency ordering for "time to first N documents" in a real gallery; this should be measured on a few real user galleries (e.g. recall of documents after scanning 10/25/50% of images).
- Could not confirm whether `getGeneration` values survive MediaProvider database rebuilds on OriginOS without a version change (AOSP says a version change signals reset).
